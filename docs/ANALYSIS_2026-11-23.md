# SynthCraft deep analysis (2026-11-23)

Scope: full read of all 15 Rust files (7,447 lines), docs, scripts and git history at commit c36aa38 (main, clean tree, 9 commits, all dated 2026-11-23). Verified by running `cargo test --workspace` and the xtask CI gates on Goliath. I did not listen to audio and did not launch the GUI. Where I analysed the two demo WAVs I used numeric measurements only.

## Verdict

SynthCraft is a well-structured, lint-clean offline synthesis and control layer with a good command-bus design and a large amount of GUI. It is not yet an instrument: nothing in the app can produce sound live, the CLAP "bridge" is a JSON document, and several headline claims in the README, HELP and MCP tool text are stronger than what the code does. The fixes are mostly days, not weeks, but the first three below change what the product is.

## What is solid

- Layering is clean: core has no UI deps, mcp has none, app depends on core only. `cargo xtask layers` passes.
- `unsafe_code = forbid` and clippy `unwrap/expect/panic/todo/unimplemented = deny` hold across the workspace; clippy `-D warnings` passes.
- One `Command` enum dispatched identically by CLI, MCP and GUI-adjacent code. This is the right shape for AGENTS rule 14 and makes everything testable headless.
- Rendering is deterministic and pure (`synthesize_audio_buffer`), so tests and offline renders are reproducible.
- WAV (RIFF PCM16 mono) and SMF format 0 writers are correct at header level and tested.
- Gates: fmt, clippy, 25 tests (4 app kittest, 5 core unit, 14 core integration, 2 mcp), assets, layers all pass. deny was skipped (cargo-deny not installed); wasm step is vacuous.

## Findings, by severity

### Critical: claims versus reality

1. No live audio, no real MIDI. No cpal/rodio/midir (or any audio/MIDI crate) in any Cargo.toml. The only audio path is offline `Vec<f32>` to WAV. The "interactive 25-key keyboard" only writes the clicked note into step 0 of the sequencer and updates a status line. The MIDI input list is a hardcoded array of strings (including "Korg M1 / nanoKEY Studio") and the channel and pitch-bend sliders drive nothing. The settings tab has buffer size and latency readouts for a device that does not exist. This conflicts with AGENTS rule 15 (do not present placeholder behaviour as success). The "Oscilloscope" and "real-time" scope are computed from a 128-sample slice of an offline render.
2. CLAP "bridge" is not a plugin. `export_clap_descriptor` returns JSON. There is no `clap_entry` symbol, no cdylib target, and `forbid(unsafe_code)` makes a C-ABI entry impossible in these crates as they stand. README marks it `Implemented`. Also the parameter table has 10 entries (0x1001..0x100A, asserted by a unit test) while README and HELP say `0x1001..0x100C`; the descriptor lists features `mono, stereo, note-effect` for a mono non-polyphonic engine yet marks parameters `poly_modulatable`.
3. Rack cables are decoration. The Eurorack canvas draws `engine.rack_cables`, a fixed list from `default_rack_cables()`. Cables cannot be created, moved or deleted, and the audio path ignores them completely. The signal chain is hardwired in `synthesize_audio_buffer`.

### High: DSP correctness

4. Oscillators are naive and alias heavily (saw, square, pulse, supersaw are raw phase maths with no PolyBLEP/BLAMP or oversampling). HELP.md calls them "anti-aliased". The supersaw is four detuned saws computed as `phase*1.007` then wrapped, which is not a detune by frequency ratio of an independent phase accumulator; it only works at phase 0..1 per call and gives non-constant detune across the cycle.
5. The filter is not a 4-pole ladder. It is a Chamberlin-style state-variable (hp, bp, lp1) plus one extra one-pole lowpass (`lp_state2`). "LowPass24dB" is therefore roughly 18 dB/oct, the resonance feedback is capped at 0.88, and `f = 2 sin(pi fc/sr)` is clamped at 0.92 (stability near the top of the range is untested). `AcidResonant` is a tanh of a lp/bp sum, not a diode-ladder behaviour. Naming should say "SVF + 1-pole" or the filter should be rewritten (a Huovilainen or zero-delay-feedback ladder is a day of work).
6. Spectrum analyser is weak: it uses only the first 512 samples (10.7 ms at 48 kHz) with a rectangular window and a direct DFT per band. Bands below about 94 Hz span less than one cycle, so the low bands are not meaningful (and 40 Hz is the bottom band). The "fundamental pitch" is zero-crossing count over the whole buffer, which is meaningless for a 16-step sequence; the unit test only asserts `> 20 Hz`.
7. Slide breaks phase in the rompler and extreme layers. Those use `w = 2*pi*freq*time` with `freq = current_freq` that changes every sample during a glide, which makes the phase jump (a chirp or click) rather than integrating frequency. Core VCOs integrate phase correctly; the layers do not. Slide slew (`0.008` per sample) is also sample-rate dependent, not time-based.
8. Envelope: ADSR is per step and the next step retriggers at attack, so release is cut off by the following step unless the gate is short. There is no overlap, no polyphony, no real note-off.
9. "Rompler" has no samples. `KorgM1Program::sample_pcm` is additive/FM maths imitating names. "Karplus-Strong" is a bank of decaying sines, not a delay-line waveguide. "Buchla 259" is a sine folder plus exponential decay. The modal bar ratios (1, 2.756, 5.404, 8.933) are the genuine free-free bar values. Honest naming would be "bell/piano-ish additive voices".
10. Stem export is inconsistent. `export_djcraft_stem` accepts up to 32 bars (60 s at 128 BPM) but the renderer clamps to 15 s, so the manifest can describe audio that cannot be rendered. Sample rate in the manifest is hard-coded 48000 regardless of engine rate; cue points are fixed fractions, not derived from the patch; the manifest does not render the WAV itself. A "stem" is one mono loop.
11. Demo WAV sanity (numeric only): `demo_1990_m1_piano.wav` has DC offset 0.12, RMS 0.40 against peak 0.80 (about 6 dB crest, so very dense), and 63 percent of energy in 200-1000 Hz. `demo_show_me_love_organ.wav` is clean (DC about 0, RMS 0.075, peak 0.72). The piano one wants a DC blocker and a loudness pass. Neither file is tracked (ignored by `*.wav`), good, but both sit in the repo root.

### High: data and safety

12. Silent data loss paths in persistence:
    - `main` in the CLI does `open_or_seed(&db).unwrap_or_default()`: if the DB open or read errors (locked, corrupt), the CLI continues on factory defaults and then `save_db` rewrites the file, destroying user patches.
    - `load_from_db` drops any row that fails `serde_json::from_str` (`if let Ok`). `SynthPatch` has serde defaults only on the four newest fields, so any future added field makes old patches vanish silently. No schema version table.
    - Save is `DELETE FROM` all rows then reinsert everything, called by the GUI on every tweak (`persist_state`) on the UI thread.
    - Rack cables, MIDI depot, demos, MIDI config and the whole `StudioSettings` struct are not stored; load rebuilds them from built-ins, so settings changes are lost on restart.
13. MCP and CLI write anywhere. `render_wav_file`, `export_midi_file` take arbitrary paths. AGENTS rule 18 requires `--automation-read-root` and `--automation-write-root` and refusal outside them; the MCP entry point implements neither. An agent can overwrite any user-writable file. The MCP server also hand-rolls JSON-RPC and silently skips unparsable input lines instead of returning a parse error.

### Medium: AGENTS.md conformance and hygiene

14. Rule 22 (no trademarked feature names): user-visible and enum names use Korg M1, Buchla 259, Casio CZ, VCV Rack 2, TB-303, Serum/Vital, "Fairlight", and the MIDI Depot has "Robin S 'Show Me Love'" with a bassline. Rules 23/24: the clip names a copyrighted work and may reproduce its melodic content; I cannot verify the notes, so treat as risk and rename or drop.
15. Rule 14: several panels mutate engine state directly instead of via `Command` (piano strip, sliders in settings, depot buttons partly), so the automation interface cannot do everything a panel does. Rule 16: user text does not go through a translation system. Rule 21: custom-painted knobs, faders and step pads show no sign of accessibility roles or live regions (not verified in full). Rule 30: integration test is `tests/synth_suite.rs`, not `tests/it/main.rs`. Rules 27/28: most core integration tests assert parsing or "within -1..1", which a plausible regression would rarely break; there is no test that audio changes when a parameter changes, that a filter attenuates, that slide is continuous, or that persistence survives a bad row.
16. `AGENTS.md` "This repository" section is the unfilled template: literal "$name", no layout, no commands, no progress-log path. It lacks the rules you want in every repo (LF only, single trunk, no leftover branches, never damage existing content when applying a standard).
17. `cargo xtask ci` as written in AGENTS.md fails: there is no `.cargo/config.toml` alias (`error: no such command: xtask`). It works via `cargo run -q --manifest-path xtask/Cargo.toml -- ci`. `cargo-deny` is not installed so the licence gate is skipped.
18. Line endings: `.gitattributes` is `* text=auto eol=lf` (good) but `start.bat` is CRLF in the working tree.
19. Documentation drift. README, HELP.md, CHANGELOG, STORYTOLD_BETA_TODO and the chat panel say 6 workbenches and 14 MCP tools; code has 19 tools (the unit test is named "...14_tools" and asserts 19) and a registry of 10 workbenches with 23 subpages (tests named "six" and "twelve"). README and CHANGELOG do not mention the M1 rompler, extreme DSP, MIDI depot, Eurorack canvas or settings workbench that make up the last three commits. The in-app chat is a canned "no model selected" reply even though settings has an Ollama endpoint field; the endpoint is never called.
20. Release scripts are vendored from the craft template and justfile `release` publishes; per your rule the `-portable.zip` launcher asset is allowed only beside plain exes. `.gitignore` ignores `*.exe`, `*.zip`, `*.wav`, which is fine; `target/` is 4.2 GB locally.

## Recommended order of work

Day 1 (audio truth): add cpal output with a lock-free parameter handoff and a real-time voice (reuse `synthesize` logic by making it a stateful `Voice::process(&mut self, out)`), add midir input and replace the fake port list. This single change makes the keyboard, scope and latency settings real. Until then relabel the UI and docs honestly ("offline renderer").

Day 2 (DSP): PolyBLEP oscillators, proper ZDF ladder or rename the filter, integrate phase in rompler/extreme layers, fix slide to time-based, windowed FFT (rustfft or a small radix-2) over a long buffer, real pitch estimator (autocorrelation on a held note). Add DC blocker and a loudness-safe master.

Day 3 (safety and data): path sandbox with the two automation roots (rule 18), persistence rewrite (schema version, per-row upsert, never overwrite on load error, persist settings/cables), CLI must fail loudly instead of `unwrap_or_default`.

Day 4 (conformance and docs): rename trademarked features and drop the Robin S clip; route all panel edits through `Command`; fill AGENTS.md "This repository" including the LF and trunk rules; add the `.cargo/config.toml` xtask alias; install cargo-deny; regenerate README, HELP, CHANGELOG, tool counts from one source (derive the tool list count in a test instead of hardcoding).

Day 5 (CLAP): decide scope. A real plugin needs a separate cdylib crate that is allowed `unsafe` per rule 13 (named in the repo section), or use a safe CLAP wrapper crate if its licence is on the allowed list.

Suggested split for Claude and opencode: Claude takes Day 3 and 4 (small, careful, cross-file); opencode takes Day 1 and 2 (DSP and audio I/O, long compile cycles). Day 5 after a decision.
